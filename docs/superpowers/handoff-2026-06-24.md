## What the harness is for
A way to *feel* the STT→brain→TTS loop end-to-end and measure latency, without the mobile
device or WebSocket server. It drives the production `AgentBrain` + `AgentSession` +
`StreamingTTS`. The **safety invariant still holds**: all reasoning/escalation lives in the
text brain; this is just an alternate ingestion for local testing.

## `scripts/live_voice_loop.py` — how it works now
- **Streaming STT (realtime websocket).** Mic streams continuously to
  `client.realtime.connect(extra_query={"intent": "transcription"})`, session configured
  for `server_vad` + `gpt-4o-mini-transcribe`, pcm 24 kHz. The model transcribes **as you
  speak**; **server-side VAD** detects end-of-speech. Events used: `speech_stopped`,
  `conversation.item.input_audio_transcription.delta`/`.completed`.
- **Brain + TTS.** On each finalized transcript → `session.handle_patient_input(...)` →
  streamed TTS playback (`audio.speech.with_streaming_response`, `response_format="pcm"`),
  first audio plays on the first chunk.
- **Barge-in.** Mic stays open during playback; a local energy detector (echo-calibrated
  threshold) sets an `asyncio.Event` that aborts TTS mid-sentence, and forwards the onset
  frames to the socket so the interruption gets transcribed.
- **Echo calibration.** During the spoken greeting it measures the agent's *own* level at
  the mic (95th-percentile RMS) and sets the barge bar to `max(level*1.5, ambient_thresh)`,
  so the agent can't interrupt itself. Headphones remove the leak entirely.
- **Warm-up.** Tiny throwaway brain+TTS calls and the realtime socket open run
  concurrently with calibration, hiding cold-start.

### IMPORTANT architecture note
The **listen side bypasses the production `VoiceLoop` / `SpeechToText` pipeline** and talks
to the realtime transcription socket directly. This is a deliberate **latency experiment**,
not a product-direction change. `config.REALTIME_MODEL` is still deprecated; the product
path remains STT→text-brain→TTS so escalation/safety stays in the inspectable text brain.

## Latency findings (measured live this session)
Per-turn pipeline is serial. Original buffered pipeline vs. the streaming version:

| | end-of-speech detection | STT | brain | TTS (to first audio) | total to first audio |
|---|---|---|---|---|---|
| **Before** | 0.6 s local hangover | 1.34 s (buffered upload) | 2.74 s | 2.27 s (full synth) | **6.95 s** |
| **After (streamed)** | server VAD (`silence_duration_ms`) | ~0.25 s | ~2.7 s | ~0.30 s | **~3.25 s** |
| **After (+`tts-1`)** | server VAD | ~0.25 s | ~2.7 s | ↓ (faster TTFB) | **~3 s** ← accepted |

**The brain (`gpt-5.4-mini`, ~2.7 s) is now the dominant cost.** STT and TTS are near-instant.
`TTS_MODEL` is a constant at the top of the script: set to **`tts-1`** (real-time-optimized,
lower TTFB, ~same cost — see below, a bit more robotic, no instruction steering); flip back
to `config.TTS_MODEL` (`gpt-4o-mini-tts`) for quality. The only remaining latency lever is
brain→TTS **pipelining** (stream the brain reply and feed sentences to TTS so TTS overlaps
the 2.7 s brain time) — discussed, not built; the user finds ~3 s reasonable.

### Audio model cost (verified 2026-06 against OpenAI pricing)
Normalized to a common basis (speech ≈ 800 chars/min); none of these is where cost goes —
the brain dominates per-turn cost too. A short reply (~200 chars / ~10 s) is ~$0.003 either TTS.
| Model | Job | Billed | ≈ per min |
|---|---|---|---|
| `gpt-4o-mini-transcribe` | STT | $0.003/min | $0.003 |
| `gpt-4o-mini-tts` | TTS | $0.60/1M in-chars + $12/1M audio-out tokens | ~$0.015 |
| `tts-1` (now used) | TTS | $15/1M chars | ~$0.012 |

So swapping to `tts-1` for speed is **cost-neutral** (marginally cheaper). The brain stays
`gpt-5.4-mini` regardless — TTS and brain are independent API calls (the shared "4o-mini"
naming is unrelated).

### Audio device selection
All audio uses the **OS default** input/output (no device is hardcoded), so a connected
Bluetooth headset works automatically if it's the Windows default — the startup line prints
the chosen devices. Caveat: using a BT device as the **mic** forces the Hands-Free (HFP)
profile (mono ~16 kHz, lower quality → weaker STT); BT as **speaker** (A2DP) is fine. A
`--device` selector to pin specific devices was offered but not built.

## How to run / tune
```powershell
.venv\Scripts\python scripts\live_voice_loop.py   # Ctrl+C to quit
```
Tunables at the top of the file:
- `TTS_MODEL` (`"tts-1"`) — voice model; flip to `config.TTS_MODEL` for quality over speed.
- `SERVER_VAD_SILENCE_MS` (400) — end-of-speech patience (↓250 snappier, ↑700 more patient).
  This replaced the old local `SILENCE_HANGOVER`.
- `BARGE_MARGIN` (1.5) / `BARGE_ONSET_FRAMES` (5) — interrupt sensitivity.
- `THRESHOLD_FACTOR` / `THRESHOLD_FLOOR` — ambient speech-onset sensitivity.

### Decisions locked (user-approved)
- **Platform: Android (Kotlin).**
- **Scope: minimal bridge** — connect, `hello`, stream camera frames + mic audio up, play
  `audio_out` back, thin debug UI. No phone-side VAD/brain/safety (all stays server-side).
- **Approach A + capture seam** — one small app, a foreground Service owns the session;
  capture behind a `FrameSource` interface so MockDevice (dev) / real glasses (later) /
  optional phone-camera are interchangeable. `AudioCapture` toggles BT-SCO mic vs phone mic.

### Approved architecture (Section 1)
```
MainActivity (debug UI) → MediaBridgeService (foreground service)
  ├─ FrameSource: GlassesFrameSource (Meta DAT SDK videoStream Flow; MockDevice|real)
  │               | PhoneCameraFrameSource (optional CameraX fallback)
  ├─ AudioCapture: BT-SCO mic (or phone mic in dev) → PCM16 24 kHz → base64
  ├─ AudioPlayer:  AudioTrack → BT speaker (glasses)
  └─ BridgeSocket: OkHttp WebSocket ⇄ ws://<laptop-IP>:8765
```
Three anchors: (1) **two capture mechanisms** — camera via Meta SDK, mic+speaker via
**Android Bluetooth audio** (the SDK does NOT do audio); (2) **capture seam** for mock/real
swap; (3) **dumb pipe** — phone only moves bytes + plays audio.

### Key research findings (verified 2026-06-25, sources below)
- **Toolkit is PUBLIC developer preview** (since Dec 2025) — no invite gate. Get it at
  `developer.meta.com/wearables`: download SDK, **enable Developer Mode on glasses via the
  Meta AI app**, add to the Android project. Full features gated to "AI glasses supported
  countries"; **public publishing disabled in preview** (side-load/test only).
- **Mock Device Kit** (`mwdat-mockdevice`) → build + test the whole bridge **without
  glasses** (camera/mic/permissions simulated; not Display glasses). This is the dev driver.
- **Camera (Meta SDK):** `Wearables.initialize(context)` → `startRegistration(activity)`
  (registers with Meta AI app) → `createSession(AutoDeviceSelector())` → `CameraStream`
  with `stream.videoStream` **Kotlin Flow**; `StreamConfiguration` res HIGH/MED/LOW + FPS
  {2,7,15,24,30}. Use **LOW + 2 FPS** (server only describes every `VISION_INTERVAL`=7 s).
  Gradle (GitHub Packages): `mwdat-core`, `mwdat-camera`, `mwdat-mockdevice`. Manifest:
  Bluetooth, Bluetooth_Connect, Internet, Camera. Metadata APPLICATION_ID/CLIENT_TOKEN
  (omitted in Developer Mode). Frame data structure not documented yet — confirm at impl.
- **Audio (NOT the SDK):** glasses mic+speaker reached via **Android Bluetooth (HFP/SCO)**.
  Phone is the paired device, so Android DOES get the glasses mic (unlike Windows). HFP mic
  is mono ~8–16 kHz → **resample on-device to 24 kHz PCM16** for the server.

### The WS contract the client must hit (`src/memaide/server/ws.py`)
- **Send:** `{"type":"hello","session_id":..,"patient":{PatientContext}}` once; then
  `{"type":"frame","data_url":"data:image/jpeg;base64,…"}` and
  `{"type":"audio","pcm":"<base64 PCM16>"}`; `{"type":"bye"}` to close.
- **Receive:** `vision_context` (description/label/advisory_flags/ts), `subtitle`
  (text/role), `escalation` (reason/triggered_by), `audio_out` (base64 pcm/seq),
  `audio_error`. Server handles endpointing + reasoning + escalation.

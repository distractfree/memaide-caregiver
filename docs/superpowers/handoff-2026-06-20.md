### The data flow that now exists
One WebSocket connection per Help session carries **both** media streams. `server/ws.py`
demuxes inbound messages by `type` (`frame` → vision, `audio` → voice, `hello`/`bye` →
control; unknown/malformed ignored) and runs two concurrent tasks:
- **Vision (continuous):** `WebSocketFrameSource` → the existing `VisionPipeline`
  (throttled describe) → stores "latest scene" + echoes a `vision_context` message.
- **Voice (turn-based):** `WebSocketAudioSource` → `VoiceLoop.run()`: STT `final`
  transcript → `AgentSession.handle_patient_input(text, vision=<latest scene>, …)` →
  `subtitle` out → `TextToSpeech.synthesize()` → `audio_out` out. A TTS failure still
  delivers the `subtitle`. A silence tick → `on_silence_tick` → `escalation` message.

### The one safety invariant to remember (unchanged from Plan A)
The describer still only supplies **advisory** flags (`VisionContext.advisory_flags`).
The rule-based `flags` that drive deterministic escalation come from an **injected
`VisionCheck`** (default `StubVisionCheck` → `[]`), applied in the WS `sink` via
`ctx.model_copy(update={"flags": deps.vision_check.check()})`. So a hallucinated
`person_on_floor` from the LLM can never fire `safety/escalation.py`. The real CV
`VisionCheck` is still a later, pluggable drop-in.
